Design
System.

A component library for the Sprout calorie tracker and recipe finder, in light and dark. Every value on this page resolves from tokens.css — no hardcoded colours, sizes, or spacing. If a token changes, this page changes with it. The control in the top-right corner cycles Auto → Light → Dark; Auto follows your operating system.

Theming

There is one set of tokens, not two. Every colour in layers 2 and 3 of tokens.css is written as light-dark(<light>, <dark>), and the color-scheme property decides which half a page uses: :root declares light dark so an untouched page follows the operating system, and [data-theme] pins one. theme.js writes that attribute from localStorage while the document is still parsing, so a stored preference is in place before the first paint.

Because light-dark() resolves against the color-scheme in force where a token is used rather than where it is declared, any subtree can be pinned on its own. Both halves of every pair below are the same markup and the same stylesheet; only .theme-light / .theme-dark differ.

What the dark theme does differently

Five decisions that are not a straight swap of light values for dark ones.
RoleLightDarkWhy
--surface-inverse forest-800 sage-100 An accent panel is defined by opposing the canvas, so it mirrors rather than darkens. .card--dark, .tag--dark, the secondary button and the Scan circle all follow it, and --text-on-inverse flips with it.
--surface-camera forest-900 — unchanged The viewfinder stands in for a live camera image, not for chrome. It was always dark on purpose, so it does not mirror; it needed its own token to stop following --surface-inverse-deep.
--surface-sunken sage-200, below the card forest-700, above it Below the dark canvas there is nowhere left to go, so a well or a progress track reads by lifting off its card rather than sinking under it.
--focus-ring-color forest-900, halo lime-200 forest-50, halo forest-900 No single colour clears 3:1 against both the dark canvas and a lime button. The ring was already two-tone, so the two roles swap: the pale ring carries every dark surface, the dark halo carries lime.
--macro-*-ink splits into -ink and -deep -ink is the dry text on the card and follows the theme; -deep is the liquid fill and the label printed on it, and the fill is the same colour in both themes, so it does not.
Layer 1 is not themed. A primitive is a fixed pigment; a token that changes its own hex is no longer one. The dark theme adds primitives of its own (--dark-canvas, --dark-raised, the lit macro hues) rather than rewriting the light ones, so every ratio quoted in this guide stays true for the palette it was measured on.
Browser support. light-dark() is what makes one declaration carry both themes. It is Baseline since mid-2024 (Chrome 123, Safari 17.5, Firefox 120). Older engines drop the declaration, leaving those tokens unset — so if this page ever renders unstyled, that is the reason, and the fix is a build step that expands the pairs into two blocks, not a change to the tokens.

Failures found, and what was done

1. Lime on cream — 1.09:1. The brand lime is unusable as text or as an icon on any light surface. It is defined as a fill-only token; anywhere a "lime" text colour was needed, --text-lime (#526B0B, 5.65:1) is substituted. The streak count uses it.

2. Orange on cream — 2.65:1. The stylescape renders the "52g FAT" numeral in raw #FF6A45 on a dark background, where it reads fine. Moved to light, it fails. Raw orange is retained for shapes, dots and the over-budget ring; text uses --feedback-warning-text (#A8380F, 6.05:1).

3. The lime focus ring — 1.62:1. The obvious choice for a focus indicator was the brand lime, but WCAG 2.4.11 requires the indicator to hold 3:1 against adjacent colours. Lime-700 manages 1.62:1 on the canvas and 1.48:1 on a lime button — it would have vanished on the primary CTA, the one control where focus matters most. The ring is now --forest-900 (16.05:1 on canvas, 14.73:1 on lime: one ring that works on every surface), with lime kept as a decorative halo outside it. For the same reason the focused input border darkens to forest-900 rather than switching to lime, which would have lowered contrast against the resting --border-strong.

4. forest-500 on cream — 4.08:1. Just short of the 4.5:1 body-text threshold. Rather than darken it and lose a useful mid-tone, it is scoped: --text-tertiary is documented for ≥24px text and icons only, where the 3:1 large-text threshold applies. Body copy uses --text-secondary.

Tap targets. --tap-min: 44px is applied to every interactive element. Where a control is visually smaller than 44px — the 32px filter tags, the small button size — a transparent ::after pseudo-element stretches the hit area vertically to 44px without changing the visual size.

As a link

Every button in the prototype that navigates is an <a>, not a <button>: the back control, the screen CTAs and the "scan instead" action all move to another screen, so they must be links to keep middle-click, right-click and the browser's own history working. .btn styles both tags identically — pick the tag by what the control does, not by how it looks. A <button> is right only when the control acts on the current screen, as the favourite toggle and the "Sign out" action do.

Segmented control

The period switch on the Stats screen. It is a real role="tablist" with two role="tab" buttons, so the selected period is announced rather than merely coloured.

Selection is driven by aria-selected="true" — the lime pill comes from .segmented__option[aria-selected="true"], not from a state class. Set the attribute and the styling follows; there is no separate class to keep in sync. The unselected tab also takes tabindex="-1" so the arrow keys, not Tab, move between tabs.

Settings variant

The appearance picker on the You screen. A preference is not a view over content, so this one is a role="radiogroup" of role="radio" buttons and reports itself with aria-checked; the fill answers to either attribute, so nothing about the styling changes. .segmented--block makes it span its column instead of shrink-wrapping, and options may carry an icon beside the label.

It is the same setting as the toggle in the top-right corner, spelled out rather than cycled — a screen with room for three labels should show all three. theme.js drives both, so the control below is live: press it and this page changes with it. No option is marked checked in the markup; the script writes aria-checked and the roving tabindex from the stored mode, and the arrow keys move the selection.

Inputs & search

Fields are pill-shaped to echo the buttons. Borders use --border-strong (3.32:1), which clears the WCAG 1.4.11 non-text contrast requirement — a 1px hairline border would not.

Recipe card

The media area is a gradient placeholder standing in for a photograph. In production it is an <img> whose alt describes the dish, e.g. alt="Avocado power bowl topped with seeds and lime".

The card is width: 100% capped at --recipe-card-width, so it fills a sized parent — a grid track or a screen column — and stops at one card's width. A parent sized by its own content gives that 100% nothing to resolve against, and the card silently shrinks to whatever its longest tag happens to need. That is why the three specimens below are given the same width explicitly: without it these cards would come out at three different sizes, and the difference would be the tag text, not the component.

Macro stat cards

Each card is a vessel: --macro-value read against the nutrient's daily target (both in tokens.css) sets how full it is, and the surface is a drifting wave rather than a flat line. The fill rises from empty on load, in step with the calorie ring, then keeps a slow undulation at rest.

The text is painted twice at the same coordinates — dark on the light card, white inside the fill — and the fill is opaque and sits between them. Whatever it covers of the dark copy is gone rather than dimmed, and the white copy takes its place pixel for pixel, so a glyph the surface happens to cross stays legible on both sides of the waterline. Measured on the fill: the value clears 5.8:1 and the target line 4.9:1 at worst, against 3:1 and 4.5:1 required.

A card at or past its target has no surface left to ripple, so .macro--full flattens the fill to the brim — otherwise the crest would straddle the top edge and bite scallops out of it. Cards describing a single dish carry no target, where a level would mean nothing, so they drop both the target line and the fill.

Weekly chart

Bar heights come from a single custom property per bar, --bar, as a 0–1 fraction of the goal. Nothing about the drawing is load-bearing: the whole chart is one role="img" with an aria-label that spells out every figure, so a screen reader gets the numbers rather than seven unlabelled boxes.

A bar over the goal takes .chart__bar--over and today's takes .chart__bar--today, which adds an inset edge — today is marked by outline as well as by fill, and .chart__col--today darkens its day letter to match. .chart--wide is the month view: fewer bars, so each gets more width.

Streak modal

The streak badge in a screen header is a <button>, not a label: pressing it opens the week behind the number. The badge keeps every visual it has as a static chip — button.badge only removes the UA button styling and adds hover, active and focus states.

The panel is a native <dialog> opened with showModal(), so the browser supplies the top layer, the focus trap, Esc-to-close and the inert page behind it. Both close controls sit in a <form method="dialog"> and need no script; the one handler in components.js exists only to open the dialog and to close it when the click lands on the backdrop.

Inside, .week marks each day by shape as well as colour: a finished day is a filled check, today is the lime chip with a forest outline, and a day still to come is an empty well. Each column carries an .sr-only word so the row reads as "Mon, tracked" rather than as seven unlabelled circles.

Scan viewfinder

The camera region on the Scan screen, and the one surface that is dark in both themes. It is dark on purpose: it stands in for a live camera image, which is a media surface rather than UI chrome, so the theme's rules stop at its edge. Everything around it stays light.

The four corner brackets are one class plus a position modifier each — each corner drops the two borders it does not need and rounds the one outer angle it keeps. .viewfinder__subject is the stand-in for whatever the camera sees; the hint text below it uses --text-on-inverse-muted, the only muted grey that still passes AA on the deep forest surface.

Bottom navigation

Five destinations. The current tab is marked with aria-current="page" and gains a lime pill behind its icon — so the active state is conveyed by shape and by assistive-technology semantics, not colour alone.

The raised Scan circle is the one tab whose glyph sits on that lime rather than beside it, so it cannot keep the white it wears over its dark resting circle — white on lime is 1.17:1. Active, it swaps to --nav-fab-active-fg, the forest that lime is built to carry, at 14.73:1.

Screen header

Two headers share one class. On a detail screen .screen__header is the title row: back control, .screen__title, trailing action. On the tab screens it is the eyebrow row instead — the "TODAY" label on the left and the streak badge on the right — with the big greeting headline living below it, outside the header.

When a detail screen has a back control but no trailing action, the slot is filled by an empty .screen__header-spacer rather than left out. The header is justify-content: space-between, so without it the title would slide right and sit off-centre between the two edges. The spacer is exactly --tap-min wide, matching the icon button it stands in for.
